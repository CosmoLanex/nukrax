Architecture

JavaScript Architecture

How JavaScript is organized across the site — shared modules, feature scripts, and the conventions that keep them consistent.

No framework, no bundler

The site is plain JavaScript using native ES modules — no React, no bundler, no transpilation step. Every module is written to run directly in the browser exactly as committed to the repository.

The assets/data/ modules

Shared, non-visual logic is split into focused modules, all re-exported from one entry point:

ModuleExports
breakpoints.jsCanonical breakpoint scale, mediaQuery(), getCurrentBreakpoint().
device.jsDevice class, touch/pointer detection, reduced motion, viewport helpers.
responsive.jsfluidSize(), scaleByViewport(), debounce/throttle, rAF-batched resize.
layout.jsContainer width, gutter, spacing scale, z-index scale.
constants.jsSite metadata, JS color mirror, product registry.
utils.jsCSS var read/write, viewport checks, formatting, safe query helpers.

See Responsive Design for how these are used in practice.

Import pattern

JAVASCRIPT 
// from a root-level page:
import NUKRAX, { BREAKPOINTS, getDeviceClass } from "/assets/data/data.js";

// from a page in a subfolder, e.g. /ea/apex.html or /docs/introduction.html:
import NUKRAX from "../assets/data/data.js";

The window.NUKRAX bridge

Because module scripts execute after HTML parsing completes (like defer), a handful of small classic (non-module) inline scripts elsewhere on some pages run before a module would. data.js also assigns itself to window.NUKRAX as a convenience bridge — safe to use from anything that runs on DOMContentLoaded or later, which covers the vast majority of the site's interactive code.

Feature-scoped scripts

Interactive features each own their script: assets/infinity/infinity.js (hero animation), assets/auth/auth-widget.js (account menu), assets/ai/widget.js (chat widget), assets/community/composer.js (post composer), and assets/docs/docs.js (this documentation shell).

Performance conventions

Every scroll-linked handler in the codebase follows the same pattern: cache expensive reads (like offsetTop) outside the handler, batch work to at most once per frame with requestAnimationFrame, and skip DOM writes when nothing actually changed. See Performance for the full story.
