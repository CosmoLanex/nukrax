Architecture

Performance

The concrete scroll and rendering optimizations already shipped — and the conventions that keep new code from regressing them.

What performance work has actually been done

Rather than a general performance philosophy, this page documents the concrete optimizations already shipped on the site — useful if you're debugging a similar issue or extending one of these patterns to new code.

Scroll handler discipline

Every scroll-linked handler on the site follows the same rule: never do layout-triggering reads (like offsetTop) inside a handler that runs on every raw scroll event. Instead:

  1. 01Cache expensive reads once, recomputed only on resize (or a ResizeObserver for content-driven size changes).
  2. 02Throttle the handler to at most once per frame with requestAnimationFrame.
  3. 03Skip the DOM write entirely when the computed value hasn't changed.
JAVASCRIPT 
let sectionOffsets = Array.from(sections).map(s => ({ id: s.id, top: s.offsetTop }));
window.addEventListener('resize', () => {
  sectionOffsets = Array.from(sections).map(s => ({ id: s.id, top: s.offsetTop }));
}, { passive: true });

let active = '';
let ticking = false;
window.addEventListener('scroll', () => {
  if (ticking) return;
  ticking = true;
  requestAnimationFrame(() => {
    let cur = '';
    sectionOffsets.forEach(s => { if (window.scrollY >= s.top - 140) cur = s.id; });
    if (cur !== active) { active = cur; /* write DOM only here */ }
    ticking = false;
  });
}, { passive: true });

will-change is scoped to the animation, not permanent

Warning
A permanent will-change on many elements (for example, one per word in an animated heading) keeps that many GPU-composited layers alive for the entire page's life — long after a one-shot animation finishes — which adds avoidable compositing overhead to every scroll afterward. On NUKRAX, will-change for one-shot reveal animations is applied by JS right before the transition starts and cleared once it ends, rather than declared permanently in CSS.

No layout reads inside animation loops

Continuous requestAnimationFrame loops (like the auto-scrolling testimonial/timeline tracks) cache dimensions such as scrollWidth/clientWidth once, rather than reading them on every single frame at 60fps — recomputing only via ResizeObserver when the tracked element's size actually changes.

What was intentionally left alone

  • backdrop-filter blur on the fixed nav — inherently resamples whatever's behind it every frame while scrolling; removing that cost means removing the blur effect, which would be a visual change.
  • transition: all on hover-triggered elements — not scroll-continuous, and rewriting each to an explicit property list carries real regression risk for a benefit unrelated to scroll performance.

How to check for regressions

Tip
If you add a new scroll listener, check DevTools' Performance panel for forced synchronous layout warnings (usually shown as a red bar / “Forced reflow” label) while scrolling — that's the signal a read is happening where a write from an earlier frame hasn't settled yet.
